# Issue #2：基础工程、权限、审批与日志

这部分为自动开票、AI 催收和现金流预测提供共同的应用基础。当前示例只演示一项通用操作从创建、审批到执行的过程，名称为 `foundation_check`；它不生成真实发票、不发送催收消息，也不执行支付。

本轮不抢先定义 Issue #1 的财务数据结构。队友完成共享数据设计后，再按 [integration.md](integration.md) 对接。

## 1. 先把应用运行起来

需要 Node.js **22.13 或更高版本**，并包含 `node:sqlite`。项目使用 Node 原生 HTTP 服务和内置 SQLite，不需要安装 npm 第三方依赖。

在仓库目录打开终端，依次运行：

```sh
node --version
npm start
```

浏览器打开：

```text
http://127.0.0.1:3000
```

开发时可以用 `npm run dev`；验证代码使用 `npm test`。SQLite 在部分 Node 版本中会显示实验性功能提示；提示本身不代表启动失败。

服务默认使用以下配置：

| 环境变量 | 默认值 | 用途 |
| --- | --- | --- |
| `HOST` | `127.0.0.1` | 本机监听地址；Replit 配置使用 `0.0.0.0` |
| `PORT` | `3000` | HTTP 端口 |
| `DB_PATH` | `data/sdc-tracker.sqlite` | SQLite 文件位置 |
| `DEMO_MODE` | `true` | 开启演示账户入口 |
| `COOKIE_SECURE` | 未开启 | HTTPS 部署时设为 `1`，限制会话 cookie 通过 HTTPS 发送 |

默认数据库文件是运行数据，不应提交到 Git。停止服务后再启动，仍使用同一个数据库文件时，操作与日志会保留。不要为了演示清空共享环境的数据：当前没有重置数据的 HTTP 接口。

## 2. 演示账户怎样使用

演示模式提供两个完全合成的工作空间，每个工作空间各有三种角色。先在页面选择一个演示账户进入，之后可以切换账户检查不同角色的效果。

| 角色 | 可以做什么 |
| --- | --- |
| `operator`（操作员） | 创建操作、提交审批 |
| `reviewer`（审批员） | 批准或驳回待审批操作，执行已经批准的操作 |
| `viewer`（观察员） | 查看本工作空间的操作与日志 |

**切换账户是演示功能，不是生产身份验证。** 页面允许选择其他演示身份，是为了让小组检查权限和流程。不要用这个入口放真实客户数据，也不要把它当成已经完成的安全登录系统。

`DEMO_MODE=false` 会禁用演示入口；当前没有另外的生产登录入口。正式使用前还需要接入身份来源，并确定账号、角色和工作空间如何分配。

## 3. 按这个顺序演示一次

使用同一个工作空间中的账户完成下面步骤：

1. 用 `operator` 创建一个带标题和备注的操作，得到 `draft`（草稿）。这只是测试流程的合成内容。
2. 切换到同工作空间的 `reviewer`，尝试执行草稿。服务端应拒绝，页面或日志能看到结果；操作不能跳过审批。
3. 切回 `operator` 提交审批，状态变成 `pending_approval`（待审批）。
4. 切换为同工作空间的 `reviewer`，批准该操作，状态变成 `approved`（已批准）。
5. 继续用 `reviewer` 执行操作，状态变成 `executed`（已执行），结果和日志可以查看。
6. 再次执行同一操作，应得到冲突结果，不能重复产生成功结果。

再分别验证两个分支：

- **驳回分支：** 新建并提交另一项操作，由 `reviewer` 驳回。`rejected` 状态不能执行；如需重做，当前演示应新建操作。
- **接口失败分支：** 对另一项已批准操作选择模拟失败再执行。应返回失败，保留 `approved` 以便重试；日志记录失败，页面不能显示为执行成功。随后关闭模拟失败并重试。

最后切换到 `viewer` 和另一个工作空间：前者只能查看；后者不能读写上一工作空间的操作与日志。权限需要由后端检查，不能只依靠隐藏按钮。

## 4. 审批状态说明

```text
draft → pending_approval → approved → executed
                        ↘ rejected
```

| 当前状态 | 下一步 | 谁能执行 |
| --- | --- | --- |
| `draft` | 提交为 `pending_approval` | `operator` |
| `pending_approval` | 批准为 `approved`，或驳回为 `rejected` | `reviewer` |
| `approved` | 执行为 `executed` | `reviewer` |
| `rejected` | 当前演示不能执行或重新提交 | — |
| `executed` | 当前演示不能再次执行 | — |

执行失败不会变成 `executed`。应先查看失败记录，再决定是否重试。这个状态机属于通用审批示例，不等同于发票的“未付／部分付款／已付”等业务状态。

## 5. 日志怎么看

操作列表回答“现在是什么状态”；审计日志回答“谁在什么时候尝试了什么，结果怎样”。日志按工作空间隔离，可按操作 ID 或结果筛选：

- `success`：允许且完成的操作。
- `failure`：执行过程或接口处理失败。
- `denied`：权限或状态不允许该请求。

日志包含 `requestId`，便于把页面收到的错误与对应请求联系起来。记录中的 `actorId`、`actorName` 是操作者；`operationId` 指向相关操作。未知操作的失败记录可能没有可关联的操作。未认证请求没有可确认的工作空间，其日志不会通过工作空间日志 API 返回，需由维护者在本地数据库中排查。

这份日志用于原型内排查与演示，不等于不可篡改的合规审计系统。不要在备注、请求内容和错误信息中输入访问密钥、真实客户资料或敏感财务数据。

## 6. 数据持久化与部署限制

内部表使用 `foundation_` 前缀，避免覆盖队友的业务表：

```text
foundation_workspaces
foundation_users
foundation_sessions
foundation_operations
foundation_audit_logs
```

同一个 SQLite 文件由当前单个应用实例使用。这个基础工程适合本地演示与集成起步；在 Replit 发布前，必须确认该部署方式是否提供持久磁盘、数据库文件会不会在重启或重新发布时丢失。若运行环境不保留本地文件，应改接持久存储或托管数据库，再重新验证重启保留数据和工作空间隔离。

仓库内的 Replit 启动配置不代表已经完成线上部署、领取额度或提供使用证明。实际部署后仍需记录可访问 URL，并从其他设备检查访问和重启行为。

- [ ] 正常审批后可执行；重复执行被拦截。
- [ ] 模拟执行失败有失败日志，保留可重试状态，不显示假成功。
