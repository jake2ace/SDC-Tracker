# GitHub 项目管理流程

**目标写在 README，任务放在 Issues，进度看 Project，改动通过 Pull Request。人员由团队自己安排。**

## 看板四个状态

| 状态 | 什么时候放这里 |
|---|---|
| Todo / 待办 | 范围和完成标准已写清，还未开始。 |
| In progress / 进行中 | 已认领并开始做。每个人尽量只推进一项主任务。 |
| In review / 待验收 | 实现或材料已完成，已附 PR / 截图 / 视频，等待检查。 |
| Done / 完成 | 完成标准实际通过；代码或材料已进入 main。 |

## 每个任务都这样走

1. **先开 Issue：** 写目标、要做的事、完成标准和依赖；认领后再开始。
2. **做修改：** 代码用分支；文档可在 GitHub 网页编辑并选择新分支。
3. **开 PR：** 说明改了什么、怎么验证，链接对应 Issue。
4. **交叉验收：** 另一位成员照步骤操作，反馈结果。不会写代码也可以验收产品行为。
5. **合并与关闭：** 检查通过后合并到 main，关闭 Issue，并将看板移到 Done。

任务可以并行，但依赖的数据与接口要先约定。发现卡点直接写在 Issue 中，不用等到最后一天。

## 初始任务顺序

1. 演示案例、合成数据与接口约定。
2. 基础工程、权限、审批与日志。
3. 自动开票。
4. AI 催收。
5. 30 天现金流预测。
6. 三个功能的页面集成与端到端验收。
7. Replit 部署与 README 复现。
8. PRD、PPTX、声明、视频和最终提交检查。

先明确目标，再认领任务；用验收结果判断是否完成。
